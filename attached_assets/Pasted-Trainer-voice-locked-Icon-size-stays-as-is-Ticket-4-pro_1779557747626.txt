Ticket 4 is the big strategic move I've been waiting for. Here's the thinking behind it before I hand you the prompt, so you can push back if anything feels off:
WHY TICKET 4 MATTERS (the strategic context)
Right now your economy has a broken loop:
Players can EARN Stripes (Ticket 3 — daily bonus, Day 5 and Day 7 drops)
Players can BUY Stripes (Ticket 2 — five packs, $0.99 to $99.99)
Players can SPEND Stripes... on nothing.
That third leg is missing. Without a Stripes sink, players have no reason to buy. A poker game that sells premium currency you can't spend is a poker game that doesn't sell premium currency. Ticket 4 closes the loop.
The Profile screen already has a 7-avatar selection system from earlier polish (default + bear/bulldog/cat/fox/gorilla/wolf). Those are free. Ticket 4 adds the premium tier on top — exclusive avatars, profile frames, name color customization, and possibly table skin previews — all purchased with Stripes.
Pricing strategy in Stripes (designed against the pack tiers):
Starter Pack ($0.99) gives 60 Stripes → afford a basic cosmetic (~50 Stripes)
Small Pack ($4.99) gives 300 Stripes → afford a couple mid-tier cosmetics
Medium Pack ($9.99) gives 650 Stripes → afford an exclusive avatar + frame combo
Large Pack ($21.99) gives 1,500 Stripes → afford multiple premium items
Mega Pack ($99.99) gives 8,000 Stripes → afford basically everything in v1
That gives every pack tier a natural "what does this get me" answer in the player's head when they're staring at the Shop deciding.

Database schema additions:
cosmetic_items table (server-controlled catalog):
id (varchar, e.g., "avatar_skull_mask")
category (varchar: "avatar", "frame", "name_color")
display_name (varchar)
description (varchar)
stripes_cost (integer)
asset_path (varchar, e.g., "/cosmetics/avatars/skull-mask.png")
color_value (varchar, nullable — for name colors, hex code)
active (boolean, default true)
created_at (timestamp)
player_inventory table (what each player owns):
id (uuid)
player_id (FK with CASCADE DELETE)
cosmetic_item_id (FK to cosmetic_items.id)
acquired_at (timestamp)
equipped (boolean, default false)
UNIQUE constraint on (player_id, cosmetic_item_id) — can't own duplicates
player_profiles additions:
equipped_avatar_id (varchar, nullable — overrides the free avatar selection if set)
equipped_frame_id (varchar, nullable)
equipped_name_color_id (varchar, nullable)
cosmetic_purchases audit table:
id, player_id (FK), cosmetic_item_id, stripes_spent, purchased_at
Seed cosmetic_items on first migration with the 13 v1 items listed above.
Server endpoints (protected with requireAuth + requireSelf):
GET /api/cosmetics/catalog
Returns all active cosmetic items, organized by category
Public-readable but require auth to access
GET /api/players/:id/inventory
Returns the player's owned items + currently equipped items
requireAuth + requireSelf
POST /api/players/:id/cosmetics/purchase
Body: { cosmetic_item_id }
Validates server-side:
Item exists and is active
Player doesn't already own it (idempotent: return 409 if owned)
Player has enough Stripes
In a database transaction:
debitStripes() with reason=cosmetic:item_id
Insert into player_inventory
Insert into cosmetic_purchases audit table
Log a stripe_transactions row (already happens automatically via debitStripes)
Returns: { success: true, newStripesBalance, ownedItem }
On insufficient Stripes: 402 Payment Required with current balance
On already owned: 409 Conflict
POST /api/players/:id/cosmetics/equip
Body: { cosmetic_item_id }
Validates the player owns the item
Updates the appropriate equipped_X_id field on player_profiles based on item category
Sets equipped=true on the relevant player_inventory row (and false on previously-equipped same-category item)
Returns: { success: true, equipped: { avatar, frame, name_color } }
POST /api/players/:id/cosmetics/unequip
Body: { category: "avatar" | "frame" | "name_color" }
Sets the corresponding equipped_X_id back to null
